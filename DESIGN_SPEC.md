# OpenOutlook — Design Specification (draft for review)

Status: **Approved design baseline**, amended with owner-confirmed deletion, Hotmail Junk Cleaner and reuse decisions on 2026-09-24. Companion: `PRODUCT_REQUIREMENTS.md`. Implementation is underway; this remains the target design and its feasibility gates still apply. See `BUILD_STATUS.md` for current progress. Section 9 records how the reading pane, sanitizer profiles, image limits and failure containment are actually built, including what real hardware ruled out.

## 1. Technical direction

- **Client:** Avalonia 11, .NET 8, C#, MVVM, desktop-only process on Ubuntu 26.04; compose, reading, search and transfer operations never block UI dispatcher. Keep application/service layers platform-neutral for a later Windows build.
- **Provider access:** Microsoft Graph delegated mail API for personal accounts; Gmail REST API for consumer accounts. Use browser-based authorization-code/PKCE and native loopback callbacks. If an API integration demonstrably fails for the owner's accounts, investigate provider-supported OAuth (XOAUTH2) over IMAP for receiving and SMTP for sending, without password/basic-auth bypass. The fallback must satisfy all Must features, including offline sync and organization, before adoption; IMAP/SMTP is not a substitute for OAuth authorization. No backend server. Retry/throttle using provider guidance, with cancellation and bounded concurrency.
- **Local data:** SQLite under XDG data directory (`~/.local/share/OpenOutlook/`) for accounts, normalized message metadata, bodies, drafts, operation queue, sync cursors and full-text search (FTS5); attachment blobs stored by opaque IDs in controlled files under XDG cache/data as appropriate. App preferences under XDG config directory. Only provider OAuth tokens in desktop Secret Service/keyring, referenced by opaque account ID. Account data is not separately encrypted. Schema migrations, database backup and recovery must be designed before persistent data release.
- **Junk Cleaner:** reuse or adapt the existing cross-platform `OutlookJunkCleaner.Core` keyword/matching rules after reviewing test coverage; do not copy WPF, tray, Outlook COM or Windows-specific config paths. Run scans through OpenOutlook's Microsoft mailbox provider, tied to a real account ID and well-known Junk folder ID.
- **PST:** an adapter around the existing cross-platform `PstCore` (`net8.0`) for reading, with attach/detach archive lifecycle operations (detach closes the handle and leaves its file untouched). The owner built `PstCore` from scratch and permits incorporation and distribution; prefer a tracked source copy within the OpenOutlook repository (or equivalent reproducible source dependency) so a public checkout builds independently of the owner's filesystem. Avoid copying private PST fixtures or the WPF app unintentionally. The WPF app is *not* reused. PST writing became an implemented track (2026-10-02): flag/read edits, delete-to-Deleted-Items, confirmed permanent delete, purge and between-folder moves ship behind backup-first Editing Mode with full-CRC sealing (see section 5 and docs/pst-editing-design.md); the earlier fake move primitive is removed. Folder creation/rename/delete and MIME insertion remain unimplemented.

## 2. Project structure

Created projects: `OpenOutlook.Desktop` (Avalonia shell and OS integration), `OpenOutlook.Domain` (initial policies/cache contract), `OpenOutlook.Providers.Microsoft` (Graph read adapters), `OpenOutlook.Providers.Google` (Gmail read adapter), `OpenOutlook.JunkCleaner` (portable rules/settings), `PstCore` (owner-contributed PST source), and `OpenOutlook.Tests`. Planned components include `OpenOutlook.Storage` (SQLite/FTS, migrations and blobs) and, only if needed after feasibility work, `OpenOutlook.Providers.ImapSmtp`. PST write validation remains a separate engineering track. The prototype UI still calls some provider types directly; moving those interactions behind application interfaces is part of the target design.

## 3. Unified model and provider semantics

- `AccountId` / `StoreId` distinguish Microsoft, Google and each PST. `MessageId` includes store ID plus provider-opaque ID (PST NID alone is only unique within a PST; account IDs and canonical Gmail message IDs are not folder IDs).
- `Message`: normalized subject, sender/recipients, timestamp, body variants, attachment references, flags, server revision/ETag where available, and raw provider ID. `Location`: Microsoft folder, Gmail set of label IDs, or PST folder. Do not deduplicate independent messages solely by Message-ID header.
- Gmail's many-to-many labels are preserved in storage even though the sidebar presents folder-like views. Moving from one Gmail view to another removes/adds labels with explicit behavior; deleting normally applies Trash rather than permanently removing a message. All Mail and Inbox may show the same logical message. Microsoft and PST use true single-parent folders.
- PST metadata/body parse may be incomplete for some items; surface per-item errors and allow export when possible instead of discarding entire folders. Store dates in UTC where known and render local time; retain original provider date and raw metadata for diagnostics.

## 4. Authorization, sync and offline operations

### Microsoft

Register a public desktop client for personal Microsoft accounts; use `/consumers` authority and system browser + PKCE loopback redirect, refresh using `offline_access`. Delegated Graph `Mail.ReadWrite`, `Mail.Send` and `Contacts.ReadWrite` are planned for mail and the requested contacts/address book; `User.Read` identifies the connected account. Request no application-wide credentials. Confirm exact consent and MSAL redirect behavior against a real personal mailbox. Use Microsoft contacts as the source of truth for Hotmail; include contact lookup in compose and a contacts view with create/edit/delete. Define a separate local address book for PST-only users or contacts the owner chooses not to store in Microsoft; never merge silently. Maintain separate delta cursors for folder list and each message folder; recover from invalid cursors with full reconcile. Avoid indiscriminate full mailbox fetches every timer tick.

### Google

Use OpenOutlook-owned desktop OAuth clients, loopback redirect, PKCE/state and offline refresh. The user-facing setup asks only which provider to sign into and opens that provider's browser sign-in page; registration IDs are supplied by the build owner. Proposed least scope for read/write/send is `gmail.modify`; verify exact drafts/send/label behaviors with tests, add `gmail.labels` only if needed for label management. Permanently deleting Gmail messages is now required; verify whether this requires the broader `https://mail.google.com/` scope for Gmail API `messages.delete`, obtain explicit informed consent if so, and prevent purge until consent succeeds. Compare narrower provider-approved alternatives without claiming that ordinary `gmail.modify` is sufficient. Gmail mail scopes are restricted and may trigger verification requirements beyond personal testing; testing-mode refresh tokens can expire after seven days. Provider registration and consent/testing guidance for the build owner are part of delivery. Never put OAuth client credentials that claim secrecy into a public repository; desktop client IDs are not secrets, but refresh tokens are.

### Sync pipeline

- On first connect: enumerate folders/labels, page metadata and bodies into local cache, index text incrementally, save durable per-account progress; attachments fetch only on demand. Support cancellation and restart, rate limits, 429/5xx backoff and bounded parallel downloads.
- On subsequent sync: use Graph delta per folder and Gmail `historyId`/history API; on Gmail 404 invalid cursor or Graph invalid state, reconcile relevant mailbox without blindly replaying local edits. Rebuild FTS when database schema/search version changes.
- Queue local operations durably (`DraftSave`, `Send`, `Move`, `LabelChange`, `MoveToTrash`, `PermanentDelete`, `ReadFlag`, `AttachmentUpload`, etc.) with idempotency keys and dependency ordering. UI shows pending/failed/uncertain states. Provider response is not automatically proof that a queued send failed if timeout occurred; reconcile Sent or draft identity before any retry to avoid duplicate messages. On conflict, retain local draft and expose choices rather than overwriting silently.
- Periodic sync while online (proposed five-minute default, configurable), on startup and manual Send/Receive. Use operating system network state plus actual request success rather than trusting an online flag. No push service/back-end dependency.

### Deletion policy

Use distinct commands `MoveToTrash` and `PermanentDelete`, never a context-ambiguous generic delete in the durable queue. On Delete, inspect the selected message's current canonical location: if outside Trash, move to Trash; if in Trash, confirm permanent purge. Shift+Delete always requests confirmed permanent purge. At execution time, recheck server/PST location and revision; if an offline item changed locations, pause for review instead of escalating a queued soft delete into permanent deletion. Confirm before purging; update cache/FTS only after acknowledged outcome. Gmail multi-label Trash transitions, Microsoft Deleted Items and PST Deleted Items require separate adapters; absent PST Deleted Items must be handled safely rather than inventing an unvalidated folder. This policy is now implemented for editable PSTs exactly as written: Delete relinks into the archive's own Deleted Items (if the archive has none, the move refuses and suggests Shift+Delete rather than inventing a folder), in-trash deletes and Shift+Delete require confirmed permanent purge, and every edit runs inside a backup-first session.

### Hotmail Junk Cleaner

The existing Windows cleaner combines case-insensitive From keyword matches with optional high-importance, missing-To and on-behalf rules. Reuse only the cross-platform rule logic, normalizing Microsoft Graph sender/from/headers and representing identities when available. Graph fields may not exactly reproduce Outlook's COM *visible From*; log unavailable fields and test representative messages before enabling optional rules. Resolve the Junk folder by the provider's well-known folder identity **within each explicitly enabled Microsoft account**, never by localized display-name string or a global default mailbox.

Store per-account enable flag, keywords, options and 1–60 minute interval. Provide explicit legacy `config.json` file selection with preview and selective import; ignore legacy Windows startup/tray options. Manual Clean Now computes a stable scan snapshot and shows count plus reason breakdown, then requires confirmation and rechecks each item's folder/revision before moving it to Deleted Items. Automatic cleaning is off by default; run only when OpenOutlook is open and authorized online, never concurrently per account, and silently move matching Junk to Deleted Items with local audit entries and error counts. Avoid persisting raw sender/header/body in audit logs. Do not call `PermanentDelete` from this feature; repeat scans and interrupted runs must not double-process or touch mail outside Junk.

## 5. PST data safety and transfers

### Reader integration

Open read-only by default; sniff header/encoding/version via `PstStore.Inspect`, reject WIP and unsupported encryption, and enumerate folders/messages through `PstStore`. Index in small batches; do not load a multi-GB archive wholly into RAM. Export uses the reader, but validate EML/MIME fidelity (attachments, inline CID, header folding, unicode, embedded messages) before using it as the canonical transfer representation.

### Writer feasibility gate - OUTCOME (2026-10-02)

The gate below was answered affirmatively for Unicode PSTs and shipped. What the implementation
does about each concern raised: contents tables are rebuilt in step with every edit (flags write
both the property heap and the Contents-Table row; moves re-link rows per MS-PST 2.6.3.2.8);
unread/content counts update best-effort and Outlook recomputes them anyway; allocation uses only
existing free slots from a BBT-authoritative occupancy map with hard no-split refusal when full -
the file never grows or shrinks in v1; every write recomputes affected block/page CRCs, and the
session seal re-verifies every BT page CRC and every block trailer (signature, payload CRC, bid
echo) before closing, auto-restoring the .bak backup on any failure; independent reopen is proven
by tests that close, reopen and re-verify after each committed edit. The three owner archives are
mandatory test cases: rmarrash_2.pst drives the fixture suite (399/399), and all three carry
captured read-only integrity baselines with md5 checks proving non-target files are untouched by
every run. Deviation from the proposed strategy: instead of a temporary writable working archive,
editing happens in place behind an upfront full-file .bak plus verify-or-restore sealing - chosen
because atomic replacement of multi-GB archives across filesystems is exactly what the gate warns
against, while backup-first + seal-or-roll-back gives equivalent recoverability without doubling
disk churn mid-edit. Password/WIP PSTs remain out of scope; ANSI (97-2002) stays read-only.
Remaining for full gate closure: an independent third-party reader pass (libpff/java-libpst) over
edited archives, and the real Windows Outlook open test - both listed as outstanding follow-ups in
docs/pst-editing-design.md. Original gate text retained below as written at review time.

Before committing to a writer strategy, inventory actual MS-PST structure updates for each action: node/subnode trees, property contexts, folder hierarchy, contents/associated tables, unread counts, allocation maps, checksums, and recovery. Compare behavior with the current reader and independently reopen using classic Outlook. `PstCore` currently writes some flags and parent relationships without rebuilding contents tables; that is **not** sufficient to assume Outlook will display correct folders or counts. Folder creation, rename, deletion (including nonempty-folder confirmation and safe handling of descendants), reparenting and message ingestion require new capabilities, not just UI calls. All three owner-supplied PSTs must pass the read/write and Windows Outlook gate, not just a subset.

Proposed safety strategy (subject to feasibility): exclusive access; snapshot or copy to a temporary writable working archive on the same filesystem; verify sufficient space; apply a bounded transaction/batch; flush and close; independently reopen and verify structures and affected identities/counts; preserve a recoverable original backup and replace the user-visible archive only after validation. Do not promise an atomic replacement across filesystems or when the PST is simultaneously opened in Windows/network shares. If the large-file copy cost is unacceptable, redesign with a proven journal/transaction scheme **and** equally strong test evidence rather than skipping backup. Surface supported format matrix; **the three supplied owner archives are mandatory editable test cases**. Refuse writes on any other unvalidated/archive format rather than risking corruption. Password/WIP PSTs remain out of scope.

### Copy/move between stores

A durable transfer manifest records source and destination IDs, stable message fingerprint, target folder/label, stage, results and errors. Convert source message to RFC 5322/MIME with correctly reconstructed attachments/inline resources; provider imports use supported Graph/Gmail mechanisms (confirm fidelity, sent dates and server IDs experimentally); PST imports require validated writer API (intra-PST moves are implemented as spec re-link with verified sealing; cross-store transfer via MIME import remains unimplemented). **Copy:** upload/write destination, read back key properties and attachments, then mark successful. **Move:** perform verified copy and only then delete/trash source after explicit confirmation; on error leave source intact and provide retry/undo where feasible. Define duplicate policy as skip/keep both/ask with conservative default; no silent loss and no cross-provider atomicity claim. Archive-to-account and account-to-archive use identical safety state machine but provider-specific adapters.

## 6. Interface specification

- Familiar classic Outlook composition rather than a literal ribbon clone: title/account search at top; compact ribbon-like Home tab with New, Reply, Reply All, Forward, Delete, Move, Mark, Send/Receive, and optional Print; sidebar folders/accounts/PSTs; center list with sender/subject/date/unread/flag/attachment; right reading pane. Toolbar adapts to PST capabilities; disabled actions explain why. Save main window geometry/maximized state, pane divider positions and message columns as local view settings; restore only to a visible screen. Reading-pane off/below options remain feasible extensions.
- Options: light and dark modes, selectable accent palette with contrast-aware foregrounds, and a persisted text-size slider/step controls affecting navigation, list, reading, compose and ribbon UI; ensure layout reflows rather than clipping. Provide a system-theme follow option if feasible, while explicit light/dark selection is required.
- PST sidebar: Add/Open PST and Remove/Detach PST actions; never delete the archive file on detach. Keep a private per-user list of attached archive paths under the XDG config directory, reopen them read-only at startup, and retain unavailable paths for a later retry. Context actions create, rename, move and delete folders inside an attached PST; nonempty folder deletion shows an item-count/descendant warning.
- Compose window: To/Cc/Bcc, subject, body, attachments, From account selector and optional per-account signature editor supporting both plaintext and sanitized rich HTML; draft autosave; explicit send queue state. Confirmation for account deletion, PST destructive edits and source-deleting moves.
- Message renderer: show complete HTML/rich-text mail and embedded/remote images by default in the reading pane and separate resizable message window. Preserve the sender's layout as closely as practical, allow full-length reading, and explain individual image failures without dropping the rest of the message. Isolate the renderer from stored tokens and native application privileges. Ordinary HTML and image display must not require a safe/trusted mode choice. Keep **View original here** as an additional in-app choice for active message content such as scripts; validate that mode's isolation before release. Provide a plaintext alternative, interactive links, text selection, zoom and print. Never interpolate untrusted HTML directly into Avalonia controls with broad privileges. How the two reader modes deliver this -- including coordinate-based text selection over browser-laid-out tiles and **Open in browser** for native selection, find-in-page and printing -- is specified in section 9.
- Print: render print-safe message view and invoke Ubuntu system print dialog, including Print to PDF. Evaluate Avalonia printing/platform interop during feasibility spike; do not assume built-in print dialog provides complete HTML/PDF fidelity.
- Status: per-account sync progress, offline/queued badges, unread counts, optional notifications, search-index progress, transfer report and PST read-only/safety indicator. Options include Junk Cleaner account selection, keywords, optional rules, import, auto-clean interval, Clean Now count-and-confirm, and local audit history. Delete and Shift+Delete shortcuts reflect Trash-aware semantics with confirmation for permanent purge.

## 7. Verification plan

- Provider adapter contract tests with synthetic mail: nested folders, many Gmail labels, Unicode, HTML/inline images, attachments, conflicting edits, drafts, timeout during send, rate limit, cursor expiry and token revocation. Test confirmed hard-delete with required Gmail scope, Trash-aware Delete/Shift+Delete and offline stale-location safety. Test Junk Cleaner matching, missing Graph fields, account isolation, manual count-and-confirm, opt-in timer, migration preview, interrupted run and audit without touching real mail. End-to-end tests against owner's primary Hotmail and Gmail accounts only with permission and non-destructive test mail.
- PST tests on disposable copies of **each** of the three supplied archives: inspect format, parse sample folders/messages, verify attachment extraction, search/export, run each edit including nested folder create/rename/delete, and compare before/after structures and actual classic Outlook views. Never add real email/PST content to version control or logs. Test process interruption, lock contention and insufficient disk on copies. Scale profiling on ~2.6 GB archive; record lack of ~4 GB fixture until resolved.
- Offline tests: disconnect during draft edit, mutation, send and transfer; restart; reconnect; verify no duplicate sends and no source deletion without confirmed destination. Run Avalonia UI smoke tests in the available headless Linux environment (for example with a virtual display where needed): launch, navigate with keyboard, exercise panes, compose, reader HTML sandbox, light/dark contrast, accent selection, text scaling and screenshots. Headless tests complement but do not replace the clean Ubuntu desktop packaging check, owner-authorized live OAuth tests, or classic Outlook on Windows PST compatibility checks. `scripts/headless-smoke.sh` is that harness and is built to three rules it violated once each: launch only on a private display (refusing to run if none is free) so a test can never open a window on the owner's session, run under a scratch HOME that is deleted afterwards so a run cannot rewrite the owner's geometry or preferences, and keep Xvfb, app, capture and cleanup in one process tree. Step types cover clicks with waits, wheel, typing, key combinations, drags (the way text is really selected) and `clip:name`, which dumps the clipboard to prove a copy happened. **Two documented blind spots: Xvfb is pure X11, so it cannot exercise the embedded web view's Wayland behaviour, and Avalonia's clipboard under Xvfb reports success while serving nothing.** Neither may be used as evidence about those two things; both need one check on real hardware.
- Release gate: all Must requirements and privacy checks pass; owner approves PST compatibility evidence and account sign-ins; self-contained Linux x64 tarball/launch script starts on clean Ubuntu 26.04 without separate .NET runtime; docs explain OAuth setup and cache behavior.

## 8. Risk register / open decisions

1. **PST writer is critical path.** Existing source lacks safe folder creation/message import; Outlook compatibility may require substantial MS-PST work. A technical spike may force scope/schedule revision, but not a silent reduction of first-release requirements.
2. **Transfers need faithful MIME conversion and provider import semantics.** Round-trip differences (read flags, recipients, dates, custom properties, labels) need an explicit mapping and acceptance examples.
3. **Gmail OAuth restricted scopes.** Personal use with a GitHub source repository is different from distributing a verified shared OAuth client; document who registers credentials, testing-mode refresh expiry and verification path if distribution changes.
4. **Linux HTML and print integrations.** Prototype sandboxed renderer and Print-to-PDF on Ubuntu 26.04 before final UI framework choice is locked.
5. **Credential and storage limitations.** If keyring is unavailable, fail account connect clearly; mail cache remains readable by the Linux account. On shared machines, OS account security matters.
6. **License/source boundary resolved by owner.** The owner states `PstCore` is original work and permits reuse, modification, incorporation and distribution in OpenOutlook. Include its code as a reproducible source dependency under the MIT-licensed OpenOutlook project; keep private PST test archives out of Git.
7. **OAuth protocol fallback.** If Graph/Gmail APIs are blocked for the owner's accounts, evaluate provider-supported OAuth over IMAP/SMTP against a full feature parity matrix; protocol selection cannot waive offline, drafts, folders/labels or transfer requirements.
8. **Permanent Gmail deletion and consent.** Owner-requested hard delete may require broader Gmail OAuth scope and greater Google verification burden; confirm exact scopes/behavior experimentally and surface clear consent, with no silent fallback to a weaker or unauthorized operation.
9. **Junk Cleaner parity.** Outlook COM visible From fields may not all be available through Graph; document mapping and safely disable checks when identity/recipient data is missing. The owner confirms they wrote `OutlookJunkCleaner.Core` and permits adapting, incorporating and publishing that source with OpenOutlook under MIT; review it before copying and retain only portable matching/configuration logic and tests.
10. **No interactive HTML widget on this display server.** An embedded web view cannot composite into an Avalonia window under Wayland, and the failure is invisible to every in-app check, so the reading pane has no native text engine here. Current design works around it (browser-laid-out snapshot plus computed selection, `Open in browser` for native affordances); the durable fix is CEF with off-screen rendering at roughly 150-250 MB of shipped dependency and ownership of input forwarding, selection painting and per-message sandbox policy. See section 9 and `docs/reading-pane-text-selection.md`.
11. **UI-thread exceptions still end the process.** Avalonia 11.2 has no central unhandled-exception hook, so an exception escaping any of the ~19 `async void` handlers in the main window reaches the platform loop and closes the application -- during compose that means a lost draft unless the save-on-close path ran. Logging and `CrashNotice` exist; per-handler containment is outstanding (tracked in `BUILD_STATUS.md`). Until then, no claim of crash resilience should be made for the desktop shell.

## 9. Reading pane rendering, diagnostics and failure containment

Implementation notes for the parts of the design that have been built and corrected against real hardware. The reading-pane story in full -- Wayland constraint, ruled-out experiments, CEF cost/benefit -- lives in [`docs/reading-pane-text-selection.md`](docs/reading-pane-text-selection.md); this section records the architecture decisions and does not duplicate it.

### Two reader modes, and why the snapshot is the default

- **Snapshot reader** (default for connected mail). `SafeHtmlDocument` turns untrusted mail into a bounded, inert document; headless Chrome/Chromium (`BrowserHtmlRenderer`) lays that document out in a short-lived process with request interception aborting every network request and JavaScript disabled unless the user explicitly chose *View original here*, then screenshots it into consecutive 3,000-pixel tiles (20 tiles / 60,000 pixels maximum) which Avalonia displays. Layout fidelity comes from using a real browser engine, at the cost of producing pixels rather than text.
- **Interactive reader** (`Avalonia.Controls.WebView`, WebKitGTK). Real HTML in an embedded widget, so selection and copy are native -- but under Wayland it embeds as a *native child window*, and Wayland has no equivalent of X11 `XReparentWindow`: nothing composites into the Avalonia window. The document loads and its scripts run while the user sees stale pixels, and every in-app check (navigation completed, content probe inside the page) reports success, so the failure cannot be detected and fallen back from automatically. Ruled out on real hardware: `WEBKIT_DISABLE_DMABUF_RENDERER=1`, `WEBKIT_DISABLE_COMPOSITING_MODE=1`, `GDK_BACKEND=x11`.
- Consequences of that split: connected Microsoft mail starts on the snapshot; interactive is an explicit per-message opt-in (**Use interactive reader** / **Use alternate reader**) so the risk sits with the person who can see it. **Headless Xvfb is pure X11, where reparenting works, so an Xvfb run proves nothing about this failure** -- a change justified that way shipped a blank reading pane and was reverted. The strategic fix is Chromium embedded with off-screen rendering (CEF), which removes the child window instead of adding another fallback.
- Open inconsistency in the current build: the snapshot-by-default rule covers connected mail only (`_preferSnapshotForMessage = _activeGraphMessage is not null`), so a PST HTML message still attempts the embedded reader first. Because the in-page content probe succeeds even when nothing composites, that path cannot fall back on its own, and under Wayland a PST message is expected to show an empty pane until **Use alternate reader** is clicked (read from code; not yet re-checked on hardware). Either extend the snapshot default to every source or remove the WebKit path -- another probe would not help, since the failure is invisible from inside the application.

### Text selection computed from geometry, not delegated to the toolkit

Because the snapshot is a bitmap, `BrowserHtmlRenderer` asks Chrome, in the same render pass, for the rectangle and text of every element holding direct text (rectangles of an element's own text nodes are unioned, so nested markup such as a bold word inside a paragraph becomes its own block; hidden elements return no rectangles and drop out). `ReadTextAreas` validates that report before anything reaches the screen -- non-finite coordinates, off-page or oversized rectangles and absurd text lengths are dropped, with 400,000 characters / 4,000 blocks as the ceiling -- because the numbers come from a rendered untrusted document.

`HtmlPageView` turns the validated rectangles into interaction: press inside a block selects it, drag extends across every block the swept rectangle intersects, `Ctrl+A` selects all blocks on that tile, `Ctrl+C` copies. Which block a point falls in, and in what order the chosen text is emitted, is decided by `TextSelectionGeometry`: reading order comes from block coordinates (top-to-bottom then left-to-right) rather than document index, so table cells copy correctly regardless of markup order, and overlapping blocks resolve to the smallest so a word inside a paragraph can be picked alone. Keeping those rules in a control-free class is what makes them unit testable without a display.

Selection is deliberately **not** delegated to `SelectableTextBlock`: Avalonia does not hit-test invisible text drawn over the picture, so a drag started there could never begin (clicks passed through to the layer beneath). Everything here is drawn by Avalonia, so behaviour is identical on X11, XWayland and Wayland. Accepted limits: block granularity rather than arbitrary character ranges (mapping a substring of one text node to the several line boxes it spans needs font metrics we do not share with Chrome), `Ctrl+A` scoped to the visible tile, and link buttons taking clicks first so words inside a link are selected by dragging across surrounding blocks.

**Open in browser** (`BrowserDocumentWriter`) is the escape hatch for native text handling: the same sanitized document the snapshot renders is written to `Path.GetTempPath()/openoutlook-reader` as a `0700` directory and `0600` file, previous message copies pruned on each open so reading mail does not accumulate other people's correspondence, and handed to the system browser. Only the renderer changes -- scripts stay disabled, remote images stay blocked.

### Two sanitizer profiles, one per direction of travel

- **Reader profile (`SafeHtmlDocument`)** is for mail arriving from outside: everything active is removed, all image URLs are stripped before a browser sees them and only validated bytes return as data URIs, a restrictive CSP plus request interception blocks network access, and links are carried inertly as `data-openoutlook-url` markers until the UI decides they may open externally.
- **Compose profile (`ComposeHtml`)** is for bodies the user is authoring, which must round-trip intact because they become what other people receive. The stock `HtmlSanitizer` it replaced was wrong in both directions: it dropped formatting the editor itself emits (`<font face>`, `mailto:` hrefs, `data:` images) while still permitting `<form>`/`<input>`, so a replied-to or forwarded message could plant a fake credential prompt in the user's own draft. The dedicated profile keeps the toolbar's formatting vocabulary -- including the border longhands AngleSharp expands the `border` shorthand into, whose omission silently deleted every bordered table in a signature -- allows http/https/mailto and image data URIs narrowed afterwards to real image MIME types with a size cap so `data:text/html` cannot ride along on an href, removes form controls, and flattens opaque `rgb()`/`rgba()` to hex because Outlook's Word-based rendering engine ignores that syntax (genuinely transparent colours are left alone rather than guessed). Sanitizing already-sanitized output returns the same string, since a body passes through it into the editor and again on Apply.

### Image handling limits

Per image: 8 MiB encoded, 16 million decoded pixels, at most 64 sources per message and 48 MiB of bytes. Because `SafeInlineImage.Validate()` can only read the dimensions a file *declares* and every other cap counts encoded bytes, `DecodedPixelBudget` reserves declared pixels from a per-message total **before** decoding; the ceiling is `SafeInlineImage.MaximumMessagePixels`, 64 megapixels (deliberately generous -- an earlier 32 MP draft dropped legitimate photo-heavy mail), enforced with `Interlocked` so parallel batches cannot oversubscribe it. Images past the budget keep their placeholder and the status line says they were skipped to limit memory rather than implying damage.

### Diagnostics and failure containment

- **`AppLog`** is an append-only rotating log (2 MB, one `.1` generation kept) at `$XDG_DATA_HOME/OpenOutlook/logs/openoutlook.log`, falling back to `~/.local/share`. It records startup, normal exit and exceptions with type, message, inner exception and stack. Every operation swallows its own errors: a full disk or read-only home must not turn logging into the failure. Its purpose is to guarantee a last word after the app vanishes, not to be a logging framework.
- **Runtime handlers** record `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException`; unobserved task exceptions are marked observed so independent background reader loads cannot take the process down.
- **Known gap:** Avalonia 11.2 exposes no `Application.UnhandledException`, so there is no central hook for an exception escaping an `async void` event handler -- it reaches the platform loop and terminates the process. Containment therefore has to happen per handler; `CrashNotice` (type, message, inner chain, bounded stack trace, **Copy details**, window stays alive) exists but is not yet wired to any handler. Wrapping the UI handlers is outstanding work, tracked in `BUILD_STATUS.md`.
- **`SafePick`** wraps all eight file/folder picker call sites. On Linux pickers talk to a portal service that can be absent, slow or shut down mid-request; a throw used to escape every handler, so opening an archive or saving an export could close the application with no explanation. A failure now returns an empty result -- exactly what "the user cancelled" already means to these callers -- and is logged. The optional status-bar report callback exists but no call site passes it yet, so a broken chooser currently looks like a cancel.
- **Fail-closed navigation.** Where native web content is shown (the reading pane's web view and the interactive message dialog), navigation is cancelled unless it is the document's own `about:` load; anything recognized as an approved link is handed to the system browser and everything else is blocked. An unclassifiable target must never be allowed through: the interactive dialog previously returned without cancelling in that case, letting an unvetted destination navigate inside a window opened for trusted mail with the message subject in its title bar.
- **Reader CSS ordering.** Author CSS is rewritten before an approved background data URI is appended. Running the generated `data:` value back through the URL replacer keyed its prefix a second time, never matched the loaded-image table and emitted `background-image: none`, which stripped the banner from every Outlook header composed with `background=`.
