# OpenOutlook — Design Specification (draft for review)

Status: **Approved design baseline**, amended with owner-confirmed deletion, Hotmail Junk Cleaner and reuse decisions on 2026-09-24. Companion: `PRODUCT_REQUIREMENTS.md`. Implementation is underway; this remains the target design and its feasibility gates still apply. See `BUILD_STATUS.md` for current progress.

## 1. Technical direction

- **Client:** Avalonia 11, .NET 8, C#, MVVM, desktop-only process on Ubuntu 26.04; compose, reading, search and transfer operations never block UI dispatcher. Keep application/service layers platform-neutral for a later Windows build.
- **Provider access:** Microsoft Graph delegated mail API for personal accounts; Gmail REST API for consumer accounts. Use browser-based authorization-code/PKCE and native loopback callbacks. If an API integration demonstrably fails for the owner's accounts, investigate provider-supported OAuth (XOAUTH2) over IMAP for receiving and SMTP for sending, without password/basic-auth bypass. The fallback must satisfy all Must features, including offline sync and organization, before adoption; IMAP/SMTP is not a substitute for OAuth authorization. No backend server. Retry/throttle using provider guidance, with cancellation and bounded concurrency.
- **Local data:** SQLite under XDG data directory (`~/.local/share/OpenOutlook/`) for accounts, normalized message metadata, bodies, drafts, operation queue, sync cursors and full-text search (FTS5); attachment blobs stored by opaque IDs in controlled files under XDG cache/data as appropriate. App preferences under XDG config directory. Only provider OAuth tokens in desktop Secret Service/keyring, referenced by opaque account ID. Account data is not separately encrypted. Schema migrations, database backup and recovery must be designed before persistent data release.
- **Junk Cleaner:** reuse or adapt the existing cross-platform `OutlookJunkCleaner.Core` keyword/matching rules after reviewing test coverage; do not copy WPF, tray, Outlook COM or Windows-specific config paths. Run scans through OpenOutlook's Microsoft mailbox provider, tied to a real account ID and well-known Junk folder ID.
- **PST:** an adapter around the existing cross-platform `PstCore` (`net8.0`) for reading, with attach/detach archive lifecycle operations (detach closes the handle and leaves its file untouched). The owner built `PstCore` from scratch and permits incorporation and distribution; prefer a tracked source copy within the OpenOutlook repository (or equivalent reproducible source dependency) so a public checkout builds independently of the owner's filesystem. Avoid copying private PST fixtures or the WPF app unintentionally. The WPF app is *not* reused. PST writing is a dedicated engineering track; existing in-place flag/move/delete functions are not production-ready proof of correctness, and there is no demonstrated folder-creation or MIME-insertion API.

## 2. Project structure

Created projects: `OpenOutlook.Desktop` (Avalonia shell and OS integration), `OpenOutlook.Domain` (initial policies/cache contract), `OpenOutlook.Providers.Microsoft` (Graph read adapters), `OpenOutlook.Providers.Google` (Gmail read adapter), `OpenOutlook.JunkCleaner` (portable rules/settings), `PstCore` (owner-contributed PST source), and `OpenOutlook.Tests`. Planned components include `OpenOutlook.Storage` (SQLite/FTS, migrations and blobs) and, only if needed after feasibility work, `OpenOutlook.Providers.ImapSmtp`. PST write validation remains a separate engineering track. The prototype UI still calls some provider types directly; moving those interactions behind application interfaces is part of the target design.

## 3. Unified model and provider semantics

- `AccountId` / `StoreId` distinguish Microsoft, Google and each PST. `MessageId` includes store ID plus provider-opaque ID (PST NID alone is only unique within a PST; account IDs and canonical Gmail message IDs are not folder IDs).
- `Message`: normalized subject, sender/recipients, timestamp, body variants, attachment references, flags, server revision/ETag where available, and raw provider ID. `Location`: Microsoft folder, Gmail set of label IDs, or PST folder. Do not deduplicate independent messages solely by Message-ID header.
- Gmail's many-to-many labels are preserved in storage even though the sidebar presents folder-like views. Moving from one Gmail view to another removes/adds labels with explicit behavior; deleting normally applies Trash rather than permanently removing a message. All Mail and Inbox may show the same logical message. Microsoft and PST use true single-parent folders.
- PST metadata/body parse may be incomplete for some items; surface per-item errors and allow export when possible instead of discarding entire folders. Store dates in UTC where known and render local time; retain original provider date and raw metadata for diagnostics.

## 4. Authorization, sync and offline operations

### Microsoft

Register a public desktop client for personal Microsoft accounts; use `/consumers` authority and system browser + PKCE loopback redirect, refresh using `offline_access`. Delegated Graph `Mail.ReadWrite` and `Mail.Send` are expected, with optional `User.Read` only if genuinely needed for account identity. Request no application-wide credentials. Confirm exact consent and MSAL redirect behavior against a real personal mailbox. Maintain separate delta cursors for folder list and each message folder; recover from invalid cursors with full reconcile. Avoid indiscriminate full mailbox fetches every timer tick.

### Google

Use OpenOutlook-owned desktop OAuth clients, loopback redirect, PKCE/state and offline refresh. The user-facing setup asks only which provider to sign into and opens that provider's browser sign-in page; registration IDs are supplied by the build owner. Proposed least scope for read/write/send is `gmail.modify`; verify exact drafts/send/label behaviors with tests, add `gmail.labels` only if needed for label management. Permanently deleting Gmail messages is now required; verify whether this requires the broader `https://mail.google.com/` scope for Gmail API `messages.delete`, obtain explicit informed consent if so, and prevent purge until consent succeeds. Compare narrower provider-approved alternatives without claiming that ordinary `gmail.modify` is sufficient. Gmail mail scopes are restricted and may trigger verification requirements beyond personal testing; testing-mode refresh tokens can expire after seven days. Provider registration and consent/testing guidance for the build owner are part of delivery. Never put OAuth client credentials that claim secrecy into a public repository; desktop client IDs are not secrets, but refresh tokens are.

### Sync pipeline

- On first connect: enumerate folders/labels, page metadata and bodies into local cache, index text incrementally, save durable per-account progress; attachments fetch only on demand. Support cancellation and restart, rate limits, 429/5xx backoff and bounded parallel downloads.
- On subsequent sync: use Graph delta per folder and Gmail `historyId`/history API; on Gmail 404 invalid cursor or Graph invalid state, reconcile relevant mailbox without blindly replaying local edits. Rebuild FTS when database schema/search version changes.
- Queue local operations durably (`DraftSave`, `Send`, `Move`, `LabelChange`, `MoveToTrash`, `PermanentDelete`, `ReadFlag`, `AttachmentUpload`, etc.) with idempotency keys and dependency ordering. UI shows pending/failed/uncertain states. Provider response is not automatically proof that a queued send failed if timeout occurred; reconcile Sent or draft identity before any retry to avoid duplicate messages. On conflict, retain local draft and expose choices rather than overwriting silently.
- Periodic sync while online (proposed five-minute default, configurable), on startup and manual Send/Receive. Use operating system network state plus actual request success rather than trusting an online flag. No push service/back-end dependency.

### Deletion policy

Use distinct commands `MoveToTrash` and `PermanentDelete`, never a context-ambiguous generic delete in the durable queue. On Delete, inspect the selected message's current canonical location: if outside Trash, move to Trash; if in Trash, confirm permanent purge. Shift+Delete always requests confirmed permanent purge. At execution time, recheck server/PST location and revision; if an offline item changed locations, pause for review instead of escalating a queued soft delete into permanent deletion. Confirm before purging; update cache/FTS only after acknowledged outcome. Gmail multi-label Trash transitions, Microsoft Deleted Items and PST Deleted Items require separate adapters; absent PST Deleted Items must be handled safely rather than inventing an unvalidated folder.

### Hotmail Junk Cleaner

The existing Windows cleaner combines case-insensitive From keyword matches with optional high-importance, missing-To and on-behalf rules. Reuse only the cross-platform rule logic, normalizing Microsoft Graph sender/from/headers and representing identities when available. Graph fields may not exactly reproduce Outlook's COM *visible From*; log unavailable fields and test representative messages before enabling optional rules. Resolve the Junk folder by the provider's well-known folder identity **within each explicitly enabled Microsoft account**, never by localized display-name string or a global default mailbox.

Store per-account enable flag, keywords, options and 1–60 minute interval. Provide explicit legacy `config.json` file selection with preview and selective import; ignore legacy Windows startup/tray options. Manual Clean Now computes a stable scan snapshot and shows count plus reason breakdown, then requires confirmation and rechecks each item's folder/revision before moving it to Deleted Items. Automatic cleaning is off by default; run only when OpenOutlook is open and authorized online, never concurrently per account, and silently move matching Junk to Deleted Items with local audit entries and error counts. Avoid persisting raw sender/header/body in audit logs. Do not call `PermanentDelete` from this feature; repeat scans and interrupted runs must not double-process or touch mail outside Junk.

## 5. PST data safety and transfers

### Reader integration

Open read-only by default; sniff header/encoding/version via `PstStore.Inspect`, reject WIP and unsupported encryption, and enumerate folders/messages through `PstStore`. Index in small batches; do not load a multi-GB archive wholly into RAM. Export uses the reader, but validate EML/MIME fidelity (attachments, inline CID, header folding, unicode, embedded messages) before using it as the canonical transfer representation.

### Writer feasibility gate

Before committing to a writer strategy, inventory actual MS-PST structure updates for each action: node/subnode trees, property contexts, folder hierarchy, contents/associated tables, unread counts, allocation maps, checksums, and recovery. Compare behavior with the current reader and independently reopen using classic Outlook. `PstCore` currently writes some flags and parent relationships without rebuilding contents tables; that is **not** sufficient to assume Outlook will display correct folders or counts. Folder creation, rename, deletion (including nonempty-folder confirmation and safe handling of descendants), reparenting and message ingestion require new capabilities, not just UI calls. All three owner-supplied PSTs must pass the read/write and Windows Outlook gate, not just a subset.

Proposed safety strategy (subject to feasibility): exclusive access; snapshot or copy to a temporary writable working archive on the same filesystem; verify sufficient space; apply a bounded transaction/batch; flush and close; independently reopen and verify structures and affected identities/counts; preserve a recoverable original backup and replace the user-visible archive only after validation. Do not promise an atomic replacement across filesystems or when the PST is simultaneously opened in Windows/network shares. If the large-file copy cost is unacceptable, redesign with a proven journal/transaction scheme **and** equally strong test evidence rather than skipping backup. Surface supported format matrix; **the three supplied owner archives are mandatory editable test cases**. Refuse writes on any other unvalidated/archive format rather than risking corruption. Password/WIP PSTs remain out of scope.

### Copy/move between stores

A durable transfer manifest records source and destination IDs, stable message fingerprint, target folder/label, stage, results and errors. Convert source message to RFC 5322/MIME with correctly reconstructed attachments/inline resources; provider imports use supported Graph/Gmail mechanisms (confirm fidelity, sent dates and server IDs experimentally); PST imports require validated writer API. **Copy:** upload/write destination, read back key properties and attachments, then mark successful. **Move:** perform verified copy and only then delete/trash source after explicit confirmation; on error leave source intact and provide retry/undo where feasible. Define duplicate policy as skip/keep both/ask with conservative default; no silent loss and no cross-provider atomicity claim. Archive-to-account and account-to-archive use identical safety state machine but provider-specific adapters.

## 6. Interface specification

- Familiar classic Outlook composition rather than a literal ribbon clone: title/account search at top; compact ribbon-like Home tab with New, Reply, Reply All, Forward, Delete, Move, Mark, Send/Receive, and optional Print; sidebar folders/accounts/PSTs; center list with sender/subject/date/unread/flag/attachment; right reading pane. Toolbar adapts to PST capabilities; disabled actions explain why. Dividers resize and persist, with reading-pane off/below options if feasible.
- Options: light and dark modes, selectable accent palette with contrast-aware foregrounds, and a persisted text-size slider/step controls affecting navigation, list, reading, compose and ribbon UI; ensure layout reflows rather than clipping. Provide a system-theme follow option if feasible, while explicit light/dark selection is required.
- PST sidebar: Add/Open PST and Remove/Detach PST actions; never delete the archive file on detach. Context actions create, rename, move and delete folders inside an attached PST; nonempty folder deletion shows an item-count/descendant warning.
- Compose window: To/Cc/Bcc, subject, body, attachments, From account selector and optional per-account signature editor supporting both plaintext and sanitized rich HTML; draft autosave; explicit send queue state. Confirmation for account deletion, PST destructive edits and source-deleting moves.
- Message renderer: isolated/sanitized HTML (WebView or equivalent vetted renderer chosen via security prototype), remote images blocked until approved; disable script execution, privileged URI schemes, local file access and arbitrary navigation. External links require clear confirmation/open in system browser. Plaintext fallback. Never interpolate untrusted HTML directly into Avalonia controls with broad privileges.
- Print: render print-safe message view and invoke Ubuntu system print dialog, including Print to PDF. Evaluate Avalonia printing/platform interop during feasibility spike; do not assume built-in print dialog provides complete HTML/PDF fidelity.
- Status: per-account sync progress, offline/queued badges, unread counts, optional notifications, search-index progress, transfer report and PST read-only/safety indicator. Options include Junk Cleaner account selection, keywords, optional rules, import, auto-clean interval, Clean Now count-and-confirm, and local audit history. Delete and Shift+Delete shortcuts reflect Trash-aware semantics with confirmation for permanent purge.

## 7. Verification plan

- Provider adapter contract tests with synthetic mail: nested folders, many Gmail labels, Unicode, HTML/inline images, attachments, conflicting edits, drafts, timeout during send, rate limit, cursor expiry and token revocation. Test confirmed hard-delete with required Gmail scope, Trash-aware Delete/Shift+Delete and offline stale-location safety. Test Junk Cleaner matching, missing Graph fields, account isolation, manual count-and-confirm, opt-in timer, migration preview, interrupted run and audit without touching real mail. End-to-end tests against owner's primary Hotmail and Gmail accounts only with permission and non-destructive test mail.
- PST tests on disposable copies of **each** of the three supplied archives: inspect format, parse sample folders/messages, verify attachment extraction, search/export, run each edit including nested folder create/rename/delete, and compare before/after structures and actual classic Outlook views. Never add real email/PST content to version control or logs. Test process interruption, lock contention and insufficient disk on copies. Scale profiling on ~2.6 GB archive; record lack of ~4 GB fixture until resolved.
- Offline tests: disconnect during draft edit, mutation, send and transfer; restart; reconnect; verify no duplicate sends and no source deletion without confirmed destination. Run Avalonia UI smoke tests in the available headless Linux environment (for example with a virtual display where needed): launch, navigate with keyboard, exercise panes, compose, reader HTML sandbox, light/dark contrast, accent selection, text scaling and screenshots. Headless tests complement but do not replace the clean Ubuntu desktop packaging check, owner-authorized live OAuth tests, or classic Outlook on Windows PST compatibility checks.
- Release gate: all Must requirements and privacy checks pass; owner approves PST compatibility evidence and account sign-ins; self-contained Linux x64 tarball/launch script starts on clean Ubuntu 26.04 without separate .NET runtime; docs explain OAuth setup and cache behavior.

## 8. Risk register / open decisions

1. **PST writer is critical path.** Existing source lacks safe folder creation/message import; Outlook compatibility may require substantial MS-PST work. A technical spike may force scope/schedule revision, but not a silent reduction of first-release requirements.
2. **Transfers need faithful MIME conversion and provider import semantics.** Round-trip differences (read flags, recipients, dates, custom properties, labels) need an explicit mapping and acceptance examples.
3. **Gmail OAuth restricted scopes.** Personal use with a GitHub source repository is different from distributing a verified shared OAuth client; document who registers credentials, testing-mode refresh expiry and verification path if distribution changes.
4. **Linux HTML and print integrations.** Prototype sandboxed renderer and Print-to-PDF on Ubuntu 26.04 before final UI framework choice is locked.
5. **Credential and storage limitations.** If keyring is unavailable, fail account connect clearly; mail cache remains readable by the Linux account. On shared machines, OS account security matters.
6. **License/source boundary resolved by owner.** The owner states `PstCore` is original work and permits reuse, modification, incorporation and distribution in OpenOutlook. Include its code as a reproducible source dependency under the MIT-licensed OpenOutlook project; keep private PST test archives out of Git.
7. **OAuth protocol fallback.** If Graph/Gmail APIs are blocked for the owner's accounts, evaluate provider-supported OAuth over IMAP/SMTP against a full feature parity matrix; protocol selection cannot waive offline, drafts, folders/labels or transfer requirements.
8. **Permanent Gmail deletion and consent.** Owner-requested hard delete may require broader Gmail OAuth scope and greater Google verification burden; confirm exact scopes/behavior experimentally and surface clear consent, with no silent fallback to a weaker or unauthorized operation.
9. **Junk Cleaner parity.** Outlook COM visible From fields may not all be available through Graph; document mapping and safely disable checks when identity/recipient data is missing. The owner confirms they wrote `OutlookJunkCleaner.Core` and permits adapting, incorporating and publishing that source with OpenOutlook under MIT; review it before copying and retain only portable matching/configuration logic and tests.
