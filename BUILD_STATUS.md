### Known-broken or outstanding (explicit)

1. **An exception escaping an `async void` UI handler still terminates the process.** Avalonia 11.2 exposes no `Application.UnhandledException` event, so there is no central hook; `AppDomain`/`TaskScheduler` handlers record it but cannot stop the exit. `CrashNotice` (type, message, bounded stack trace, **Copy details**) is implemented but has **no call sites yet**, so today nothing shows it. Routing the 19 `async void` handlers in `MainWindow` (22 across the app) through a `SafeUi`-style wrapper is outstanding work, not done.
2. **Selection granularity is the text block.** No arbitrary character range; `Ctrl+A` covers the visible tile only; link buttons take their clicks first, so words inside a link cannot be selected by pressing on them. These follow from not sharing Chrome's font metrics and are stated in `docs/reading-pane-text-selection.md`.
3. **The embedded web view is unusable under Wayland.** WebKitGTK loads the document and its scripts run, but nothing composites into the Avalonia window, so the pane shows stale pixels while every in-app check reports success. Ruled out on real hardware: `WEBKIT_DISABLE_DMABUF_RENDERER=1`, `WEBKIT_DISABLE_COMPOSITING_MODE=1`, `GDK_BACKEND=x11`. Consequence: connected mail defaults to the snapshot reader; interactive is opt-in per message. CEF with off-screen rendering is the documented strategic fix.
   - **Follow-on gap (read from code, not yet re-checked on hardware):** the snapshot-by-default rule was restored only for connected mail (`_preferSnapshotForMessage = _activeGraphMessage is not null`). A PST HTML message still tries the embedded reader first, and its content probe succeeds inside the page even when nothing composites -- so on a Wayland desktop a PST message is expected to show an empty pane until **Use alternate reader** is clicked. Either default PST mail to the snapshot too, or fix the paint; the fallback cannot detect this case.
4. **`SafePick` logs failures but does not report them visibly.** All eight picker call sites pass only two arguments, so the optional status-bar callback is unused; a portal failure looks like a cancelled dialog.
5. Unchanged from before: no background sync or full-text index, no PST writes, Gmail adapter only (no account integration), Junk Cleaner previews but never cleans, no native print dialog.

## Reader text selection, browser hand-off and failure containment (2026-09-30)

The full story for this group -- the Wayland constraint, what was ruled out by experiment, and CEF with off-screen rendering as the strategic fix -- is in `docs/reading-pane-text-selection.md`. It is not repeated here.

- Interactive-reader default reverted after real-hardware failure: making the embedded web view the default left the reading pane blank for the owner while every check inside the app reported success (the content probe runs in the page, and a native child surface cannot be captured from Avalonia). The change had been justified by an Xvfb run; Xvfb is pure X11, where reparenting works, so it could not have found this. Connected mail is back on the snapshot renderer, and the code comment now records that **an Xvfb run proves nothing about this failure**.
- Selectable text over the snapshot: headless Chrome already knows where it laid out every piece of text, so `BrowserHtmlRenderer.RenderDocumentAsync` now reports leaf-block rectangles and their text in the same render pass, validated by `ReadTextAreas` (non-finite, off-page, oversized and absurd-length entries dropped; 400,000 characters / 4,000 blocks maximum). `HtmlPageView` turns those rectangles into a selection -- press inside a block, drag to extend across swept blocks, `Ctrl+A` for the tile, `Ctrl+C` to copy -- with order taken from coordinates rather than document index so table cells read correctly, and overlapping blocks resolving to the smallest so a bold word inside a paragraph can be picked alone. The ordering and containment rules live in `TextSelectionGeometry`, which holds no controls and is unit tested; rectangle validation is tested separately. Selection is computed rather than delegated to `SelectableTextBlock` because Avalonia does not hit-test invisible text drawn over the picture (clicks passed straight through). Works in the main pane and the pop-out window. Confirmed on real hardware by the owner, clipboard copy included; under Xvfb Avalonia's clipboard reports success while serving nothing, so it is not a valid test surface for this.
- **Open in browser** (`BrowserDocumentWriter`, reading-pane toolbar): writes the same sanitized document that the snapshot renders to `Path.GetTempPath()/openoutlook-reader` -- directory `0700`, file `0600`, documents beyond 64 M characters refused -- and hands it to the system browser, where selection, find-in-page and printing are native. Previous `message-*.html` copies are pruned on each open so reading mail does not accumulate other people's correspondence; pruning is best-effort and leaves unrelated files alone. Scripts stay disabled and remote images stay blocked: only the renderer changes. The check recorded when this landed was a real message written at 655,860 bytes, mode 600, zero script tags; unit tests cover the file mode, pruning of earlier messages only, and refusal of empty or oversized documents.
- Compose fidelity: `ComposeHtml` is a sanitizer profile built for outgoing bodies instead of the stock `HtmlSanitizer` the editor used before, which was wrong in both directions -- it dropped formatting the editor itself produces (`<font face>`, `mailto:` hrefs, `data:` images) while still permitting `<form>`/`<input>`, so a replied-to message could plant a fake credential prompt in the user's own draft. The new profile keeps the toolbar's formatting vocabulary including the border longhands AngleSharp expands `border` into, allows http/https/mailto and image data URIs narrowed to real image MIME types with a size cap so `data:text/html` cannot ride along on an href, drops form controls, and flattens opaque `rgb()`/`rgba()` to hex because Outlook's Word-based engine ignores that syntax (genuinely transparent colours are left alone rather than guessed). Sanitizing is idempotent, since the same body passes through it into the editor and again on Apply. An early draft of the profile omitted `src` from allowed attributes and dropped every image; the tests caught it.
- Inline image memory budget: `SafeInlineImage.Validate()` only trusts the dimensions a file declares and the loader's other caps count encoded bytes, so many tiny files each declaring a huge bitmap could decode to roughly 4 GB of RGBA merely by selecting the message. `DecodedPixelBudget` now reserves declared pixels per message before decoding (thread-safe via `Interlocked`, ceiling `SafeInlineImage.MaximumMessagePixels` = 64 megapixels; an earlier 32 MP draft was rejected because it dropped 64 inline photos at 1200x800). Images past the budget keep their placeholder, and the status line says they were skipped to limit memory rather than implying damage.
- Table background images restored: `SafeHtmlDocument.Build()` appended the resolved data URI for a `background=` attribute and then ran that same string through `ReplaceCssUrls`, which keyed the `data:` prefix a second time, never matched the loaded-image table, and emitted `background-image: none`. Author CSS is now rewritten first and the already-safe data URI appended after. Outlook composes many message headers this way, so they had lost their banners.
- Logging and crash handling: `AppLog` writes a rotating 2 MB log (`openoutlook.log`, one `.1` file kept) to `$XDG_DATA_HOME/OpenOutlook/logs/` falling back to `~/.local/share`, records startup and normal exit, and swallows every error it hits itself -- a full disk or read-only home must not turn logging into the failure. `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` are recorded, with unobserved tasks marked observed so background reader loads cannot take the process down. `CrashNotice` renders an exception's type, message, inner chain and a bounded 12-frame stack trace with a **Copy details** button, keeping the window alive; **it is not yet called from anywhere**, which is why item 1 above stays open.
- File pickers: all eight call sites (seven in `MainWindow`, one in `ComposeWindow`) now go through `SafePick`. On Linux pickers talk to a portal service that can be absent, slow or shut down mid-request, and the throw used to escape every handler -- opening an archive or saving an export could close the application with no explanation. A failed picker returns an empty result, which is exactly what a cancelled dialog already means to these callers, and logs it; the optional status-bar report callback exists but no call site passes it yet.
- Corrupt archives: `PstException` was added to the catch filter around single-message EML export so a damaged archive surfaces as a status message instead of escaping as an unhandled crash (the attachment-export path already listed it, and archive open has always caught everything).
- Fail-closed navigation in the interactive message dialog: the guard used to return without cancelling when `SafeHtmlDocument.TryLink` could not vet a target, letting an unclassifiable destination navigate inside a window opened for trusted mail with the message subject in its title bar. Now only the document's own `about:` load is allowed; anything else recognized as a link goes to the system browser and everything else is cancelled. This matches the reading-pane web view's guard.
- Headless harness (`scripts/headless-smoke.sh`): runs the real app on a private Xvfb display under a scratch HOME that is deleted afterwards, refuses to run at all if no private display can be allocated so it can never open a window on the owner's session, forces window geometry after launch so scripted coordinates mean the same thing every run, and supports `OO_SMOKE_LIVE=1` (a copy of `accounts.json` in the scratch HOME for real-account runs; the refresh token comes from the keyring over the inherited session bus and nothing is written back), `OO_SMOKE_PANES` for deterministic pane weights, and step types `x,y:seconds`, `wheel:x,y:n`, `type:text`, `key:combo`, `drag:x1,y1,x2,y2` and `clip:name` (dumps the clipboard to prove a copy happened). **Harness blind spots, both learned the hard way:** Xvfb cannot exercise the embedded web view's Wayland behaviour, and Avalonia's clipboard under Xvfb reports success while serving nothing. Neither is valid evidence about those two things.

6. **Contain exceptions that escape UI handlers.** Route the 19 `async void` handlers in `MainWindow` (22 across the app) through a `SafeUi`-style wrapper that logs, shows `CrashNotice` and keeps the window alive; Avalonia 11.2 provides no central hook, so this has to be done per handler. 7. **Decide the interactive reading pane.** Either embed Chromium with off-screen rendering (CEF/`Cglue`), which removes the Wayland child-window constraint entirely and is the documented strategic fix, or drop the WebKit path so there is one reader whose behaviour is known on every display server.
